# RCL v0.5 Continuity Profile and Behavioral Signature

## Purpose

RCL distinguishes **task semantics** from **behavioral identity**.

A task can succeed while still feeling unlike the source robot. `ContinuityProfile` and `BehavioralSignature` are the first v0.5 IR layer for representing that difference explicitly.

```text
Behavior / Intent
what the robot is trying to do

BehavioralSignature
how this robot characteristically does it
```

The central question is no longer only:

> Can Robot B perform the task?

It also becomes:

> Can Robot B perform the task while preserving the characteristic manner learned by Robot A?

## ContinuityProfile v0.1

A ContinuityProfile belongs to one source robot and contains one or more context-aware BehavioralSignatures.

It records:

- source robot identity;
- optional source embodiment identity;
- evidence references;
- behavioral signatures learned from repeated interaction.

The profile is deliberately **not** a required `.rcl` v0.2 package payload yet. The five-payload archive boundary remains unchanged while the v0.5 continuity IR matures.

## BehavioralSignature v0.1

A BehavioralSignature describes observed traits for one behavior in one context.

Example:

```text
FOLLOW_USER

following_distance = 0.82 m
lateral_offset = +0.18 m
acceleration_style = soft
turn_delay = 170 ms
gaze_before_move = true
approach_speed = 0.74 m/s
stop_overshoot = 0.03 m
```

Each trait may retain confidence, observed sample count, units, and evidence references.

A signature describes **what has been observed**. It does not yet say how important the trait is to identity.

## Separation from IdentityConstraint

This boundary is intentional:

```text
BehavioralSignature
= observed behavioral identity

IdentityConstraint
= preservation policy / importance
```

For example, `gaze_before_move=true` belongs in the signature. A later IdentityConstraint may declare that the trait has importance `0.95`, permits substitution, but does not permit post-migration adaptation.

Keeping these concepts separate prevents measurement data from being confused with migration policy.

## Context

The same behavior may have different signatures in different contexts.

For example:

```text
FOLLOW_USER / home
FOLLOW_USER / outdoor
```

v0.1 uses exact matching for caller-supplied context fields and rejects ambiguous selection rather than silently choosing a signature.

## Compatibility

This work does not change:

- `.rcl` package format `0.2`;
- the five existing package payloads;
- Behavior/Intent semantics;
- existing embodiment adapters;
- HIL evidence grading.

Instead it adds a new continuity IR that later compatibility mapping and the behavior-preserving compiler can consume.

## Next layer

The next planned layer is `IdentityConstraint`, followed by capability-aware compatibility mapping:

```text
ContinuityProfile
→ BehavioralSignature
→ IdentityConstraint
→ CapabilityManifest
→ EXACT / APPROXIMATE / SUBSTITUTE / UNSUPPORTED
→ ContinuityScore
→ Embodiment Compiler
→ observed post-migration evaluation
```
