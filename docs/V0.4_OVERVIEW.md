# Robot Continuity Layer v0.4 — Overview

**Experimental open specification · semantic/reference implementation line `0.4.0-dev`**

> **Hardware can be replaced. Experience shouldn't be.**

This document is the concise, external-facing overview of the RCL v0.4 capability surface.

RCL is an experimental open specification and reference implementation for carrying a robot's **portable continuity** across hardware changes: identity metadata, preferences, semantic behavior, habits and history, declared functional intent, familiar expression, long-lived experience evidence, and the provenance needed to review those claims.

RCL does **not** try to make Robot B mechanically imitate every limitation of Robot A. The new body should use its own better sensors, actuators, controllers, planners, and safety systems while preserving the purpose, experience, and recognizable manner that should survive the hardware change.

## 30-second explanation

```text
Robot A lives with a user
        ↓
experience / preferences / habits / WHY / expression accumulate
        ↓
RCL stores portable semantic continuity
        ↓
Robot A is replaced
        ↓
Robot B imports the continuity profile
        ↓
Robot B uses its own native hardware to perform the real function
        +
preserves familiar behavior where safe and feasible
        ↓
RCL measures what was preserved, what changed, and why
```

The compact mental model is:

> **Use the new body. Preserve the old manner.**

## Package compatibility

The semantic/reference implementation line is `0.4.0-dev`, but the `.rcl` archive container intentionally remains compatible with the existing package format.

A packaged profile still contains exactly:

```text
manifest.json
identity.json
preferences.json
behavior.json
skills.json
embodiment.json
```

The package-format identifier remains the existing RCL `0.2` format. v0.4 extends the semantics carried inside the five payloads and adds companion evidence/governance artifacts; it does not add a sixth required profile payload or silently break older package readers.

## The six semantic questions

RCL v0.4 separates concepts that are often accidentally mixed together:

```text
WHY      → functional Intent / Goal
WHAT     → portable semantic behavior + parameters
HOW      → embodiment adapter / target-native execution strategy
LOOKS    → visible expression / familiar gesture
TEMPO    → expressive temporal style
HISTORY  → habit / legacy / prior interpretations / prior expressions
```

Example:

```text
WHY
verify the sitting area is clear before sitting

V1 HOW
turn rearward and inspect with a camera

V2 HOW
use direct rear depth sensing

V1/V2 LOOKS
brief familiar rearward glance may still remain

TEMPO
natural target-native timing rather than copied motor slowness
```

The functional check can improve on V2 while the familiar gesture remains as expression when it is safe and representable.

## Five continuity principles

RCL v0.4 is organized around five practical rules:

> **Use the new body. Preserve the old manner.**
>
> **Preserve the gesture, not the limitation.**
>
> **Preserve by default. Optimize only by explicit approval.**
>
> **Recommend automatically. Change only by explicit approval.**
>
> **Preserve the goal, not one body's capability recipe.**

These rules deliberately put safety and real target capability ahead of blind imitation.

## The v0.4 lifecycle

The complete software/spec picture can be read as one pipeline:

```text
Robot operation
    ↓
Experience Episodes
    ↓
optional non-destructive Compaction
    ↓
Experience Retention / Archive review
    ↓
Provenance / Privacy governance
    ↓
RAW or AGGREGATE Habit Evidence
    ↓
Habit lifecycle review + explicit approval
    ↓
WHY hypothesis from human / rule / LLM / VLM
    ↓
Intent Discovery
    ↓
Context Diagnostics
    ↓
Explicit Intent Approval
    ↓
Intent Revision / history when interpretation changes
    ↓
Goal Vocabulary Governance when a project wants a shared standard goal
    ↓
Alternative Capability Paths
    ↓
Adapter Migration + Conformance
    ↓
Target-native execution on Robot B
    ↓
Observed Intent Success
    ↓
Repeated Intent Success across trials/sessions
    ↓
optional Expression Optimization Recommendation
    ↓
explicit Expression simplify/remove approval
    ↓
old expression remains in append-only history
```

No one stage is allowed to silently substitute for another.

## Experience: remember events without storing everything forever

RCL records lightweight semantic episodes such as:

```text
Context + Action + Outcome
```

Raw image/video/audio is not embedded in the Experience Store. A deployment may keep external evidence and point to it through references.

Experience Compaction can turn repeated episodes into deterministic aggregate statistics while retaining provenance and representative exemplar IDs.

Compaction is explicitly non-destructive:

> **Compaction is not deletion consent.**

A summary does not authorize deleting its source evidence.

## Retention: long-lived memory needs a lifecycle

After compaction, RCL can classify source episodes as:

```text
RETAIN
ARCHIVE_CANDIDATE
PRUNE_CANDIDATE
```

`PRUNE_CANDIDATE` does not mean deleted. It means a later explicit deployment workflow may consider pruning the episode under the selected policy.

The conservative reference policy protects recent evidence, summary exemplars, externally referenced evidence, sparse groups, and a deterministic active remainder.

Archive Records are also modest by design: they record a deployment assertion that an external copy exists, but RCL does not claim to have inspected remote storage bytes.

## Provenance and privacy: lineage is not permission

RCL v0.4 can bind companion provenance/privacy records to JSON artifacts without changing the `.rcl` payload layout.

The record can carry:

```text
artifact digest
origin / actor
parent lineage
transformation metadata
privacy classification
sharing scope
external evidence-reference handling
```

Two rules matter most:

> **Provenance is not permission.**

Knowing where data came from does not grant permission to publish or share it.

> **Aggregation does not automatically declassify data.**

A private Experience Store does not automatically produce a public Summary merely because the data was aggregated.

Reference privacy ordering is:

```text
public < internal < private < restricted
```

Derived artifacts may not silently lower the privacy classification or broaden the sharing scope inherited from governed parents.

RCL validates declared metadata and policy consistency. It does not inspect content and claim to know whether something is legally personal data, nor does it perform encryption, upload, sharing, archive, or deletion I/O.

## Habit Evidence: raw and aggregate are both useful, but not identical

Long-lived Habit review may use either:

```text
RAW Experience
→ direct source evidence

Compacted Summary
→ aggregate evidence
```

For equivalent evidence, counts/repeat rates/observation spans can be comparable, but provenance remains different.

Aggregate evidence never reconstructs pseudo-episodes and never creates synthetic `habit.events` history.

A `sufficient` Habit Evidence result means only that the repeated semantic action pattern is substantial enough to support review under a versioned engineering policy. It does not autonomously declare the behavior stable or legacy.

Habit lifecycle promotion remains a separate review step, and applying a lifecycle change requires explicit approval into a new profile snapshot.

## Intent: preserve the reason before the motion

A behavior can declare an engineering purpose:

```text
goal
trigger
success condition
failure action
criticality
capability requirements / alternatives
```

The principle is:

> **Preserve the reason before the motion.**

Intent is an engineering interpretation of why the behavior exists. It is not a claim about consciousness, subjective motivation, or personhood.

## Intent Proposers: AI may suggest WHY, but it does not decide WHY

Humans, rule engines, LLMs, VLMs, or other external systems may submit the same neutral Intent Hypothesis Proposal envelope.

```text
human / rule / LLM / VLM
        ↓
WHY hypothesis
        ↓
actual evidence remains separate
```

A model's self-reported confidence is audit metadata only.

```text
model self-confidence
≠ RCL evidence confidence
≠ approval authority
```

RCL stores a concise reviewable rationale, not hidden chain-of-thought.

The proposer may suggest the WHY. Evidence and explicit approval determine whether that WHY becomes continuity metadata.

## Intent Discovery and Context Diagnostics

Intent Discovery asks:

> Is there enough observed association evidence to review this WHY hypothesis?

It can operate on raw Experience Episodes or compatible action-stratified Experience Summaries without fabricating raw observations.

An Intent Candidate always keeps:

```text
causal_claim = false
```

Context Diagnostics asks a different question:

> Does the pooled association remain similar across narrower observed conditions?

For example:

```text
pooled association → positive
surface=table      → strongly positive
surface=tray       → neutral
```

RCL may raise a context-dependency review signal, but it does not silently reject the candidate or claim that it proved a causal confounder.

## Explicit Intent Approval and Revision

Discovery does not mutate a profile.

A candidate becomes current continuity metadata only through Explicit Intent Approval into a new immutable snapshot.

If later evidence supports a better engineering interpretation, Intent Revision creates another explicit snapshot while preserving the previous Intent in append-only history.

RCL therefore remembers not only the current declared WHY but also how that interpretation changed over time.

## Goal Vocabulary Governance

Projects remain free to experiment with private/vendor goals under extension namespaces such as:

```text
x.<owner>.<semantic_path>
```

A project-specific goal does not automatically become a shared RCL standard goal.

Shared-vocabulary promotion follows a separate proposal/review/decision workflow.

> **Experiment freely; standardize deliberately.**

An approved governance decision authorizes a later explicit vocabulary repository/spec change; the governance tool does not silently rewrite the bundled standard vocabulary.

## Alternative Capability Paths: preserve WHY, not one sensor recipe

One goal may have several valid semantic routes.

```text
same WHY
  ↓
Path A OR Path B OR Path C
  ↓
different target-native HOW
```

For example, the same clearance goal may be representable through direct clearance sensing, directional attention plus classification, or an external semantic state.

The source robot's hardware combination is not declared universally canonical.

An adapter may choose a body-appropriate satisfied path, but it must report which path and strategy it selected.

## Adapter Conformance: the HOW may differ, the report must be honest

Intent-aware Adapter Conformance independently evaluates declared capability paths against target capabilities and checks whether the adapter's preservation/path claims are truthful.

> **An adapter may choose a different HOW, but it must report the WHY and selected satisfaction path honestly.**

Conformance validates protocol/report behavior. It does not certify a physical sensor, actuator, or robot for real-world safety.

## Expression and timing: preserve familiarity without preserving defects

RCL separates the real functional mechanism from familiar visible manner.

A legacy expression can remain even when Robot B already completed the function using a better target-native system.

Expressive Timing uses semantic style such as:

```text
tempo
dwell
transition
timing policy
legacy significance
```

Historical source milliseconds are evidence, not target commands.

A source motion that was slow only because of old motors, gearing, wiring, controller latency, or power limits may be naturalized on the new body.

If the timing itself became recognized or user-valued, the temporal style may be explicitly preserved.

## Expression optimization: redundancy is not deletion permission

A familiar gesture becoming functionally unnecessary does not authorize deleting it.

RCL can produce a non-mutating optimization recommendation such as:

```text
review_removal
review_simplification
retain
inconclusive
```

The recommendation always remains separate from actual change and never claims causal redundancy was proven.

Simplifying or removing a current expression requires a separate explicit approval operation. The previous complete expression snapshot remains in append-only history.

> **Recommend automatically. Change only by explicit approval.**

## Observed Intent Success: did the robot actually satisfy WHY?

Capability-path satisfaction means:

> The target can represent one declared semantic route to the goal.

It does **not** mean the robot actually achieved the goal.

Observed Intent Success evaluates one execution against the declared trigger and success condition and can report:

```text
pass
fail
not_observable
not_triggered
```

This is separate from motion similarity and separate from adapter conformance.

## Repeated Intent Success: can the robot keep satisfying WHY?

One successful execution shows the goal can be achieved once.

Repeated-trial / repeated-session Intent Success reports how consistently the declared goal is observed as satisfied across evidence, including uncertainty.

A required failure remains explicit even when the average success rate is high.

RCL intentionally does not define one universal success-rate threshold for all robots, tasks, or safety domains.

## Four things that must not be confused

These statements answer different questions:

```text
Capability Path preserved
→ Can this body represent one declared semantic route to the goal?

Adapter Conformance passed
→ Did the adapter report the route and migration truthfully?

Observed / Repeated Intent Success passed
→ Was the declared success condition actually observed as satisfied?

Motion / Statistical Continuity matched
→ How similar was the observable behavior itself?
```

And one more question sits above all of them:

```text
Physical validation
→ Is the real robot safe and suitable in the actual environment?
```

No software report substitutes for physical validation.

## Priority order

When concerns conflict, RCL's intended priority is:

```text
Safety
  ↓
Target-native functional capability / valid goal-satisfaction path
  ↓
Honest adapter reporting / conformance
  ↓
Observed / repeated Intent Success evidence
  ↓
Legacy behavior / expression
  ↓
Optimization recommendation
  ↓
Explicit optimization/removal approval
```

Context diagnostics, provenance, privacy, and evidence lifecycle governance provide review boundaries around this execution flow; they do not reduce safety priority.

## What v0.4 does not claim

RCL v0.4 does not claim to provide:

- consciousness transfer;
- personhood transfer;
- subjective emotional continuity;
- causal proof of why a robot behaved a certain way;
- automatic legal privacy classification or consent inference;
- encryption or access-control infrastructure;
- universal robot-safety certification;
- universal reliability thresholds;
- automatic deletion or archive I/O;
- automatic AI authority over Intent;
- a universal planner, policy model, VLA, or motor-control runtime;
- a replacement for ROS 2, LeRobot, robot-learning frameworks, or vendor control stacks.

RCL is a continuity/interoperability layer that can sit above or beside those systems.

## v0.4 completion boundary

The major planned v0.4 software/spec capability areas are now represented in the reference implementation:

```text
portable semantic migration
capability registry + alternative goal-satisfaction paths
behavior Intent / goal semantics
Intent proposer / discovery / context diagnostics / approval / revision
Goal Vocabulary Governance
lightweight Experience Store + compaction
Experience retention / archive / prune review
Provenance / Privacy governance
Habit history / evidence / promotion / explicit approval
expression + expressive timing
expression recommendation + explicit optimization approval
adapter conformance
observed / statistical / repeated-session continuity
observed + repeated Intent Success
```

The **capability surface is frozen for the v0.4 polish pass**. Freeze does not mean that bugs, documentation errors, schema inconsistencies, or safety/validation defects cannot be fixed. It means new conceptual capability areas should not be added automatically before the v0.4 story, documentation, and release boundary are consolidated.

## What comes next

The next documentation step is to reconcile the large `README.md`, `ROADMAP.md`, and `CHANGELOG.md` with this overview using a safe focused editing path.

The major technical direction after v0.4 is **physical Robot A → Robot B validation (v0.5)**.

A representative validation should include:

```text
Robot A repeated real behavior
    ↓
Experience capture
    ↓
RCL profile + evidence
    ↓
Migration to a genuinely different Robot B
    ↓
Robot B uses target-native HOW
    ↓
measure functional Intent success
    +
measure behavior / expression / timing continuity
    +
repeat across trials and sessions
    +
physical safety checks
```

Human-facing interaction tests such as handover or handshake-style behaviors may be particularly useful because they can expose both functional success and recognizable continuity, but no single demo should be treated as universal proof of RCL across all robot classes.

## One-sentence summary

> **RCL lets a robot use a new body and new technology while preserving the purpose, experience, recognizable manner, and auditable history that should survive the hardware change — without pretending that representation, evidence, approval, similarity, and physical safety are the same thing.**
