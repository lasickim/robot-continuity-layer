# RCL v0.5 Hardware-in-the-Loop Reference

**Phase:** v0.5 Phase 2  
**Reference contract:** `0.1`

## Purpose

Phase 1 proved the semantic A → B continuity path using deterministic synthetic observations. Phase 2 introduces a real execution boundary without pretending that a complete physical robot exists.

The first HIL boundary is intentionally small:

```text
real edge compute / controller
        +
simulated plant
        ↓
RCL migration + repeated Intent evaluation
```

This lets a Jetson, Raspberry Pi, industrial PC, or other intended edge controller execute the same v0.5 semantic experiment while the robot body remains simulated.

## Evidence rule

A semantic PASS alone is not HIL evidence.

The HIL harness requires all of these declarations:

```text
environment = deployment
at least one real loop component
at least one simulated boundary component
at least one external evidence reference
self-declared runtime attestation
```

If any of those are missing, the report is:

```text
evidence_grade = UNCLASSIFIED
status         = not_eligible
```

even when the embedded semantic experiment passes.

This prevents CI from silently upgrading synthetic evidence to HIL evidence.

## Current reference boundary

The initial reference configuration treats:

```text
REAL
compute

SIMULATED
plant
```

as the minimum HIL boundary.

Later HIL revisions may move additional roles across the boundary:

```text
real compute + real sensor + simulated actuator/plant
real controller + simulated robot dynamics
real sensor + controller + simulated environment
```

The evidence grade must describe what was actually real in that run.

## Runtime attestation

`build_hil_runtime_attestation()` records runtime facts available from Python plus the declared real/simulated component roles.

The attestation is explicitly:

```text
attestation_trust = self_declared
```

It is not TPM-backed remote attestation, cryptographic hardware identity proof, or safety certification.

Deployments that need stronger assurance should retain external logs, signatures, device inventory, photos, or other evidence and reference them through `evidence_refs`.

## Running on the intended edge host

From the repository checkout on the actual edge computer:

```bash
python examples/v0.5-hil/run_hil_reference.py \
  --deployment \
  --component-id edge-controller-01 \
  --evidence-ref file://hil-evidence/runtime-log.json \
  --output hil-report.json
```

Without `--deployment`, the same command intentionally exits non-zero and produces an unclassified report.

A deployment run passes only when:

1. the HIL readiness contract is eligible;
2. the underlying Robot A → Robot B semantic reference experiment still passes;
3. the target uses the expected different HOW for the same WHY.

## What CI proves

Repository CI tests the HIL contract and report schemas. It proves that:

- CI/unclassified execution cannot claim HIL;
- the declared deployment contract has a valid pass path;
- runtime/public schemas remain identical;
- the existing Phase-1 semantic assertions remain embedded in Phase 2.

CI does **not** prove that a Jetson, Raspberry Pi, sensor, controller, or physical robot was actually used.

## What Phase 2 does not claim

Phase 2 does not yet prove:

- real sensor accuracy;
- actuator dynamics;
- mechanical safety;
- collision avoidance on a physical body;
- physical expression/timing fidelity;
- real Robot A → Robot B continuity.

Those remain Phase 3+ evidence.

## Next hardware increment

After the real-compute + simulated-plant run is captured, the next useful HIL step is:

```text
real edge compute
+ real sensor input
+ simulated actuator / robot body
```

That moves the perception side of the loop into hardware while still avoiding the need for a complete robot.
