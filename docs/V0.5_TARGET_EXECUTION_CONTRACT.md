# RCL v0.5 Target Adapter Execution Contract

`Target Execution v0.1` is the vendor-neutral boundary between the RCL behavior-preserving compiler and a real target robot adapter.

```text
Behavior Compiler Plan
        ↓
Target Execution Bundle
        ↓
TargetExecutionAdapter
        ↓
ROS2 / Jetson / vendor SDK / simulator
        ↓
Target Execution Report
```

## Fail-closed dispatch

RCL does not partially dispatch a behavior plan by default.

- `READY` compiler plan → dispatch allowed.
- `REVIEW_REQUIRED` compiler plan → dispatch denied.
- `BLOCKED` compiler plan → dispatch denied.

This prevents an adapter from executing only the easy portions of an identity-preserving behavior while silently omitting an unresolved or identity-critical component.

## Adapter interface

A deployment adapter implements one method:

```python
class TargetExecutionAdapter:
    def execute(self, instruction: dict) -> dict:
        ...
```

The instruction is already compiler-approved and contains the target-facing contract such as:

```text
constraint_id
behavior_id
dimension
capability_id
mapping_mode
target_value
```

or, for an evidence-resolved substitute:

```text
substitution_strategy
assessed_fidelity
assessment_evidence_refs
```

The adapter returns:

```python
{
    "success": True,
    "evidence_refs": ["..."],
    "message": "optional deployment message",
}
```

## Boundary

RCL core does not define motor commands, ROS messages, CAN frames, vendor SDK calls, or safety-certified actuator procedures. Those remain deployment-adapter responsibilities.

The execution report records dispatch success and evidence references. A successful dispatch is not by itself proof of observed behavioral continuity; later observed/HIL/physical evaluation must compare actual behavior against the source BehavioralSignature.
