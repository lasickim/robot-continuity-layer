# RCL v0.5 Camera Semantic HIL

**Phase:** v0.5 Phase 2 — Hardware-in-the-Loop  
**Bridge version:** `0.1`

## Purpose

This bridge lets a real camera and deployment perception stack produce target-side semantic evidence without putting camera SDKs, YOLO, VLMs, or vendor runtimes inside RCL core.

```text
REAL
camera + edge compute + perception runtime

SIMULATED
plant + actuator / robot body
```

## Boundary

The deployment records a `camera-perception-series`:

```text
camera identity
+ model/runtime identity
+ frame reference
+ semantic inference
+ predicate
+ confidence
+ inference evidence refs
```

RCL then converts those inferences into the generic `sensor-evidence-series` introduced in Phase 2.

## Confidence policy

The experiment declares `minimum_confidence`.

```text
confidence >= threshold
→ predicate true  => satisfied
→ predicate false => not_satisfied

confidence < threshold
→ not_observable
```

Low-confidence output is therefore not silently promoted into a semantic fact.

The threshold is experiment-specific. RCL does not define a universal camera confidence threshold.

## Example Intent

The first camera reference continues the existing v0.5 behavior:

```text
WHY
safety.verify_sitting_area_clear

semantic state
state.sitting_area_clear
```

A deployment may use classical CV, YOLO, depth vision, segmentation, a VLM, or another perception stack to make that semantic inference. The inference method and model identity remain explicit provenance.

## Evidence requirements

CI may use synthetic perception records to validate the bridge, but cannot claim deployment HIL evidence.

A real HIL run still requires the generic HIL gate:

- intended deployment environment;
- real compute and camera sensor role;
- simulated plant/actuator boundary;
- external evidence references;
- self-declared runtime attestation.

## What a successful real run can show

It can show that a real camera/perception pipeline generated target-side semantic evidence and that the existing RCL WHY/capability-path/Intent Success model consumed it successfully.

It does **not** prove model accuracy, camera calibration, complete scene coverage, occlusion robustness, collision safety, or full physical Robot A → Robot B continuity.

## Next step

Implement one deployment producer on Jetson or Raspberry Pi that captures frames, runs a chosen perception method, persists frame/inference evidence, and writes a valid `camera-perception-series`.

After that, run the existing Camera Semantic HIL bridge with `deployment=True`. Sensor fusion should remain a separate composition layer rather than hiding camera + ToF provenance inside one sensor claim.
