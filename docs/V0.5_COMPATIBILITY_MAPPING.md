# RCL v0.5 Compatibility Mapping

`Compatibility Mapping v0.1` is the first RCL layer that combines observed behavioral identity, preservation policy, and target embodiment capability into one migration-facing report.

## Inputs

```text
ContinuityProfile
+ BehavioralSignature
+ IdentityConstraint
+ CapabilityManifest
```

The mapper evaluates each constrained behavioral dimension independently.

## Classifications

### EXACT

The target declares direct support and can represent the observed source value exactly.

### APPROXIMATE

The target declares direct support, but range or resolution means the closest reachable value differs from the source value.

`APPROXIMATE` does not automatically mean policy failure. The report separately records whether the reachable target value remains inside the corresponding `IdentityConstraint` tolerance.

### SUBSTITUTE

No preferred direct route exists, but the target declares a substitute route and the source identity policy explicitly allows substitution.

A substitution is a different physical expression intended to preserve the same behavioral identity dimension. v0.1 records the declared substitution strategy; it does not yet assign a continuity score to that strategy.

### UNSUPPORTED

No usable mapping route exists. Examples include:

- no target support for the dimension;
- substitution exists but policy forbids substitution;
- unit mismatch;
- value-kind mismatch;
- a categorical source value is not supported by the target declaration.

## Classification versus policy

The central v0.1 distinction is:

```text
classification
= how the target can physically/semantically realize the trait

constraint_satisfied
= whether that realization is acceptable under identity policy
```

For example:

```text
source turn_delay = 175 ms
target resolution = 10 ms
nearest target = 180 ms

classification = APPROXIMATE
absolute error = 5 ms
```

If policy allows `±40 ms`, the constraint passes. If policy allows only `±2 ms`, the mapping remains `APPROXIMATE` but the constraint fails.

This separation is deliberate. `ContinuityScore` is the next layer and should consume both mapping class and policy/evidence information rather than collapsing them prematurely.

## Reference Robot A → Robot B

The v0.5 continuity example currently yields:

```text
following_distance   EXACT
lateral_offset       EXACT
acceleration_style   EXACT
turn_delay           EXACT
gaze_before_move     SUBSTITUTE
approach_speed       EXACT
stop_overshoot       EXACT
```

The gaze habit is identity-critical. Robot B lacks the direct gaze route used by Robot A, but its CapabilityManifest declares `body_yaw_attention_cue` as a substitute and the IdentityConstraint allows substitution.

Run the example with:

```bash
python examples/v0.5-continuity/run_compatibility_mapping.py
```

## Non-goals

Compatibility Mapping v0.1 does not:

- calculate the final ContinuityScore;
- prove that a declared substitute feels equivalent to a user;
- certify physical safety;
- infer undeclared capabilities;
- modify the `.rcl` package-format 0.2 boundary.

The next compiler layer is `ContinuityScore v0.1`, followed by target behavior compilation and post-migration adaptation.
