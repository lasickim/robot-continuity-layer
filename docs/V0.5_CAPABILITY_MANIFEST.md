# RCL v0.5 CapabilityManifest v0.1

`CapabilityManifest` describes what a target embodiment can actually realize for behavioral continuity mapping.

It is intentionally richer than the v0.2 `embodiment.json` capability string list. The existing package field remains compatible and useful for coarse capability discovery; `CapabilityManifest v0.1` is a separate v0.5 compiler IR for migration analysis.

## Why this layer exists

A behavioral trait such as:

```text
gaze_before_move = true
```

cannot be evaluated from a generic capability label such as `locomotion` or `camera`.

The compiler needs to know whether the target can implement the behavioral dimension directly, only through a declared substitute, or not at all.

```text
BehavioralSignature
        +
IdentityConstraint
        +
CapabilityManifest
        ↓
Compatibility Mapping
```

## Support declarations

Each capability declares one or more supported behavioral dimensions.

A support entry contains:

- `dimension`
- `mapping_mode`: `direct` or `substitute`
- `value_kind`: `number`, `boolean`, or `categorical`
- optional numeric range, unit, and resolution
- optional categorical allowed values
- required `substitution_strategy` for substitute mappings

### Direct example

```json
{
  "dimension": "following_distance",
  "mapping_mode": "direct",
  "value_kind": "number",
  "unit": "m",
  "minimum": 0.3,
  "maximum": 3.0,
  "resolution": 0.01
}
```

### Substitute example

Robot B has no neck/gaze actuator but can rotate its body to signal attention:

```json
{
  "dimension": "gaze_before_move",
  "mapping_mode": "substitute",
  "value_kind": "boolean",
  "substitution_strategy": "body_yaw_attention_cue"
}
```

The manifest does not itself decide whether this substitute is acceptable. That decision belongs to `IdentityConstraint.substitution_allowed` and the upcoming compatibility mapper.

## Deterministic preference

`preferred_support_for_dimension()` prefers a direct declaration when one exists. Only when no direct support exists does it return a substitute declaration.

The next compatibility layer will combine this with:

- the source trait value;
- tolerance policy;
- identity importance;
- target ranges/resolution/allowed values;
- substitution policy.

It will then emit one of:

```text
EXACT
APPROXIMATE
SUBSTITUTE
UNSUPPORTED
```

## Package compatibility

This does not modify the `.rcl` package-format `0.2` five-payload boundary. `CapabilityManifest v0.1` remains an independent v0.5 compiler IR while the model matures.
